# Mapa V1 → V2

| V1 | Destino V2 | Migração / preservação |
|---|---|---|
| Shell multi-view hash-router | SPA única com rotas internas | Manter URL GitHub Pages sob `/SAHMT-V2.0.github.io/`; preservar rótulos e ordem conhecidos. |
| Providers e experiência de login atualmente habilitados | Firebase Auth singleton | Console verificado em 25/09/2026: Google ativo; Email/Password não aparece como ativo. V2 só apresenta Google; não alterou o projeto. Um login resolve UID → `users/{uid}` → perfil/permissões e vale para todo o PWA. |
| `Code.gs` monolítico | Regras/campos necessários extraídos para serviços de domínio no cliente Firebase; sidecar pequeno e assíncrono para relatórios | Usar o código antigo apenas como referência. O PWA acessa Firestore; Apps Script V2 só recebe jobs seletivos para espelhar relatórios. Não participa de sessão, autorização, consultas do usuário ou confirmação da ação. |
| UID do Firebase ligado a usuários V1 e abas operacionais | Coleções Firestore documentadas em `FIRESTORE_SCHEMA.md` | UID identifica a sessão e o perfil `users/{uid}`; não procurar a pessoa por e-mail em cada operação. Importação de dados é separada, determinística, com preview, backup e aprovação da fonte de verdade; não executar carga produtiva automaticamente. |
| `core/outbox.js` e stores locais específicos | Repositório local IndexedDB versionado + outbox | Operações offline somente para tipos aprovados, UUID de operação, retry com backoff, deduplicação no servidor e estado visível. |
| `core/views/home.js` | Home/Escala no shell e serviço Firestore | Home abre escala/cache por UID e data, depois atualiza escala, férias e contatos sem esperar leituras independentes; manter posições, destaques, navegação e ação de liberação no cartão de contato. Calendário e catálogos importados ainda dependem de revisão e carga autorizada. |
| `core/views/eventos.js` e escalas/férias | Eventos no shell + coleções `events`, `eventCatalogs`, `scheduleDays`, `vacations` | Preservar formulários, siglas, data e regras validadas; Eventos consulta/grava no Firestore e mantém revisão/versão. Catálogo de pagadores/credores fica no módulo Eventos. Dados autorizados de escala/férias ainda aguardam conferência e carga. |
| `core/views/etiquetas.js` | Etiquetas no shell + serviços Firestore | Entrada manual, captura/foto, OCR português local como rascunho, revisão antes de salvar, edição versionada com histórico imutável por campo e relatórios CSV/PDF locais. Etiquetas com dados de paciente ficam fora do cache/outbox; leitura segue autor/sigla/`labelsManage`. Escrita autorizada exige conexão; precisão em fotos reais e comparação visual ainda pendem. |
| `core/views/gestao.js` + atividades e `DocumentRegistry.gs` | Gestão no shell + coleções de áreas, atividades, planos, indicadores e equipamentos | Manter as 12 áreas conhecidas e abrir Gestor/Equipe no mesmo PWA. A V2 tem tarefas atribuídas por UID (até 20 responsáveis de equipe para tarefas sem pontos; tarefa pontuada exige responsável único), comentários append-only, planos, medições calculadas em Rules, documentos por metadados no Drive e manutenção versionada. Conclusão de tarefa simples de Gestão usa callable transacional e regra versionada; catálogo geral V1 de fontes, evidências e recorrências será implementado uma fonte por vez, com validadores próprios. O cadastro/link do documento existe, mas validação de checksum/revisão, transição de renovação por evidência e monitoramento de alterações no Drive ainda não estão implementados; o trigger V1 correspondente era explicitamente `NOT_CONFIGURED`. |
| Checklist + ZXing + assinaturas | Checklist no shell + Firestore e callable de assinatura | Estações, QR/câmera/foto, respostas e relatórios operam no mesmo módulo. Callable deriva responsável por UID, assina snapshot/revisão imutável e lança ledger idempotente para relatório completo; escrita direta de assinatura/pontos é negada. Homologação autenticada e dados autorizados continuam pendentes. |
| Treinamentos, participações, progresso | `views/training` + `domains/training` | Preservar andamento, conclusão, evidência, pontuação e retomada offline quando permitida. `trainingStart` cria recibo com snapshot de pontos; `completeTraining` verifica 95% dos intervalos salvos e o sinal de encerramento, conclui e lança pontos em transação idempotente. O progresso local marcado como encerrado é retomado pela callable após sincronizar. Como na V1, os intervalos e o sinal vêm do player cliente; não são atestado antifraude independente. |
| Apps Script / integração Google Forms | `functions` para validações confiáveis e sidecar Apps Script mínimo para relatórios quando autorizado | Nunca usar Apps Script/Sheets para sessão, autorização, consultas de clique ou banco operacional. O sidecar seletivo atual é apenas local e não implantado; Google Forms/Drive exigem requisito concreto e validação de origem antes de integrar. |
| V1 service worker e cache | Um service worker V2 no escopo do novo Pages | Base path explícito, cache versionado, limpeza somente de caches V2 e atualização controlada. |
| Imagens, logos, ícones e CSS V1 | `assets/v1` inicialmente | Copiar apenas assets referenciados; preservar a composição da V1 e registrar cada diferença em `UI_PARITY.md`. |

## Gaps que bloqueiam migração automática

- A entrega atesta que o script ainda aguarda implantação Google; endpoints e propriedades precisam ser verificados na conta autorizada.
- O projeto Firebase informado é existente, mas a estrutura, regras, índices, provedores de Auth, usuários e dados não foram verificados no console.
- A enumeração oficial das 12 áreas, owners, permissões, listas de usuários e IDs de planilha devem vir da fonte vigente e ser validados antes do seed.
- A saída do migrador legado para Firestore deve ser revisada para evitar expor dados, duplicar registros ou sobrescrever produção.
